# How terco works

This is the algorithmic description of terco: what each stage computes, the
data structures it works on, how the work is laid out on the GPU and why it was
built that way. It is meant to be read alongside the code (paths are given
throughout) and to serve as the basis for the algorithms section of a paper.
`docs/GENERATORS.md` covers the kernel generators in more depth;
`docs/functionals.md` lists the functionals.

Numbers in brackets refer to the references at the end.

## 1. Principles

- **Standard Fortran for the compute.** Every kernel is a `do concurrent`
  loop compiled by nvfortran with `-stdpar=gpu`. OpenACC is used only to
  manage data: `enter`/`exit data`, `update`, `host_data` (to hand device
  pointers to cuBLAS, cuSOLVER and CUDA-aware MPI), `routine seq` and
  `atomic`. The single OpenACC compute construct in the code base is a
  diagnostic counting loop (`src/eri/trc_binkernel.F90`).
- **Separate memories.** The GPU build uses `-gpu=mem:separate`: host and
  device copies are distinct and every array a kernel reads must be mapped
  explicitly. Persistent device data belongs to an object that maps it and
  releases it (section 10).
- **The host build is the reference.** With the GPU off, the directives are
  comments, `do concurrent` runs on the CPU and the program must give the
  same numbers. Continuous integration builds the host library with gfortran,
  Intel and NVHPC and also runs an OpenMP translation of the code (section
  10); GPU builds are validated against the same tests.
- **Generate the hot kernels.** Integral kernels are generated per
  angular-momentum class by Python scripts in `scripts/`, with every index a
  literal, no table loads and no branches on angular momentum, so the
  compiler allocates registers for one class at a time rather than for the
  worst class of a generic kernel.
- **Never materialise quartets or integrals.** Quartets are formed on the
  device from binned shell pairs [1], and the Fock matrix is digested inside
  the integral kernel, so neither a quartet list nor an integral tensor ever
  exists.

## 3. Basis and AO spaces

`trc_basis_t` (`src/api/trc_api.F90`) is a structure of arrays: per shell the
angular momentum, primitive count, first AO, centre and owning atom, and per
primitive the exponent and coefficient. A basis is read from MolSSI Basis Set
Exchange JSON (`src/basis/trc_basis_json.F90`) or built from libcint's
`atm`/`bas`/`env` arrays.

- **Normalisation.** Primitives and contractions are normalised to unit
  overlap, and libcint's `common_fac_sp` (the s and p angular factors) is
  folded into the coefficients exactly once, in `build`, so every kernel can
  treat a coefficient as final.
- **Cartesian kernels, spherical results.** Every integral kernel works in
  the Cartesian AO space. A spherical basis is handled by folding:
  `sph_cart_to_sph` and `sph_sph_to_cart` (`src/core/trc_sph.F90`) apply the
  per-shell-pair transformation T D Tᵀ with coefficients generated by
  `scripts/gen_sph.py` from Schlegel and Frisch [2]. The SCF works in
  whichever space the basis asks for; the Fock build, XC, PCM and DF all
  receive the Cartesian density and return Cartesian matrices.
- **Cartesian order.** Component order is a build option
  (`TERCO_CART_ORDER`: lexicographic, or GAMESS order), defined once in
  `scripts/cartorder.py`, so the same source serves either convention.
- **Decontraction.** For the four-centre build a general contraction can
  be split into primitive shells, with the contraction carried as a matrix
  transform instead (`src/basis/trc_decontract.F90`): the density is
  expanded with D_p = C D Cᵀ and the result folded back with G = Cᵀ G_p C.
  Diffuse primitives (exponent ≤ 0.3, GPU4PySCF's cutoff) are treated
  separately from compact ones, and per-shell amplification factors make
  screening in the split basis bound the error in the contracted matrix.

## 4. Four-centre integrals and the Fock build

`trc_eri_t` (`src/eri/trc_eri.F90`) is built once per geometry from a basis
and a threshold τ, owns every four-centre structure on the device, and
returns the two-electron matrix for a density. The pipeline follows [1].

### 4.1 Shell pairs and Schwarz bounds

`build_pairs_hgp` (`src/eri/trc_hgp.F90`) forms the primitive pairs of every
shell pair (Gaussian product exponent, centre, prefactor), discarding
primitive pairs below τ·10⁻³. `schwarz_bounds_hgp` (`src/eri/trc_screen.F90`)
computes Q_ab = max |(ab|ab)|^½ for every shell pair on the device.

### 4.2 Binning

Shell pairs are binned (`src/eri/trc_bins.F90`) by **type** and **size**:

- type is (l_a, l_b) together with the contraction degree, so every thread
  in a launch evaluates the same class with the same primitive count;
- size is the bucket s_ab = ⌊−log₁₀ Q_ab⌋, at a resolution of 1 to 4
  buckets per decade.

Because |(ab|cd)| ≤ Q_ab Q_cd, a pair of bins is admitted if and only if
s_ab + s_cd ≤ −log₁₀ τ. The test is an integer comparison done once per bin
pair on the host, and it is conservative (truncation can only admit more).
Whole cross products of bins are admitted or rejected together, so a launch
needs no screening branch to decide whether a thread has work. Bins larger
than 32768 pairs are split, which keeps a bin-pair product below 2³¹
quartets.

Materialising the quartet list was the bottleneck this replaces: for 75
waters in 6-31G it cost 26 s of host time and 11.7 GB, against 15 s of GPU
time.

### 4.3 Launches

`fock_bins` (`src/eri/trc_binkernel.F90`) walks the admitted bin pairs and
writes one descriptor per segment (one bin-pair product): the two bins,
their offsets and the class. Segments are sorted by class, and each
contiguous run of one class is one kernel launch. Inside a launch, each
`do concurrent` iteration decodes its global index into (segment, ab, cd)
through a prefix sum and evaluates that quartet. A diagonal bin pair uses
only its lower triangle.

### 4.4 Screening inside the kernel

Bin admission is a bound on whole bins. Each quartet is then tested on its
own:

1. the exact Schwarz product Q_ab Q_cd > τ;
2. a density-weighted bound, Q_ab Q_cd · max(4D_ab, 4D_cd, D_ac, D_ad, D_bc,
   D_bd) > τ, with D the largest density element over each shell block. A
   coupled-perturbed solve switches this off (the trial densities are not
   the SCF density);
3. a primitive-quartet bound, which abandons a primitive quartet before the
   Boys function when its prefactor is below τ·10⁻³ (`TRC_PRIM_MARGIN`).

### 4.5 Integral kernels

Each class has its own generated kernel:

- **Head-Gordon–Pople** for classes up to d: an unrolled Obara–Saika
  vertical recurrence followed by the Head-Gordon–Pople horizontal
  recurrence, with every index a literal (`scripts/gen_perclass.py`, output
  `src/generated/trc_pc_k*.F90`). The Boys function is a degree-5 Chebyshev
  interpolation on 960 intervals up to T = 30, the per-order layout of [1]
  (`src/core/trc_boys.F90`).
- **Rys quadrature** for every class with an f (or higher) shell, and
  optionally for chosen lower classes (`TRC_RYS_CLASSES`). The kernels are
  spliced from the HGP kernel skeleton by `scripts/gen_rys.py`, using Rys
  roots and weights from Chebyshev tables generated with mpmath
  (`scripts/gen_rys_roots.py`). `rys_route` (`src/eri/trc_rys_select.F90`)
  picks the kernel per class.

**Chunked f classes.** A Rys kernel that holds a whole quartet block in one
thread does not fit in registers once f shells appear: for (fp|dp) one
thread held 7.5 KB of stack, and Nsight Compute measured 103 GB of local
loads and 38 GB of local stores per launch against 3.2 GB of global loads,
with SM throughput at 3.5%. The f-class kernels are therefore ordered as

    chunk of output components → primitive quartet → root

where a chunk is every component of the inner shells for one component of
each outer shell. A chunk keeps its integrals in named scalars, builds only
the part of the two-dimensional Rys table it reads, and is digested on its
own. A measured plan (`FOCK_CHUNK_PLAN`) chooses for each class whether the
chunks of a quartet run in one thread or in separate threads. On a V100 for
20 waters in cc-pVTZ at τ = 10⁻¹³ this took (fp|dp) from 137 ms to 43 ms per
launch, its stack from 7.5 KB to 136 B, and the Fock build from 2.42 s to
1.37 s (GPU4PySCF on the same system: 1.02 s), with the energy unchanged to
10⁻¹⁵.

### 4.6 Digestion

The Fock contribution of a quartet is added inside the kernel. The
symmetric build uses the eight-fold permutational symmetry of the canonical
quartet and folds J and K into one matrix, so a quartet touches six blocks of
it: two Coulomb and four exchange. The digestion is block-accumulated: the
six density blocks a quartet reads are loaded into registers once, every
integral component is contracted against them there, and each output block
is written once with atomics. For (pp|pp) that is 54 loads and 54 atomic
updates per quartet instead of 486 of each when every component is
scattered on its own. The kernel accumulates a folded half-matrix, and the
driver returns vhf = J − K/2 for the total density after symmetrising. When
the exchange weight is zero (pure DFT functionals and the Coulomb pass of an
unrestricted build) a separate branch drops the exchange gathers entirely.

A non-symmetric build (`fock_nosym`) writes J and K separately and serves
the response equations, whose trial densities are not symmetric.

### 4.7 Range separation

The long-range operator erf(ω r₁₂)/r₁₂ needed by range-separated hybrids is
obtained from the same kernels: the Gaussian product exponent ρ is replaced
by θρ with θ = ω²/(ρ + ω²), and the prefactor is scaled by θ^½ (in the Rys
kernels the substitution is applied to the root t²). ω = 0 reproduces the
Coulomb integrals bit for bit. A range-separated SCF makes a second pass
for the long-range exchange.

### 4.8 Several GPUs

Every rank builds the same bins and takes every n_ranks-th work item; the
partial Fock matrices are summed with an allreduce. One GPU is bound per
rank by node-local rank (`trc_bind_device`).

### 4.9 Nuclear gradients

The two-electron gradient (`src/eri/trc_grad.F90`) uses Rys kernels for
every class (`scripts/gen_rys_grad.py`), over the same bins. Each class runs
in two passes: a screening pass that compacts the surviving quartets into a
list, then the derivative pass over that list. Contributions are accumulated
into 32 private copies of the gradient, chosen by thread, and reduced at the
end, which limits atomic contention on the few atoms a quartet touches.

## 5. Other integrals

One-electron integrals (overlap, kinetic, nuclear attraction and their
derivatives), multipoles, PCM integrals and the two- and three-centre
density-fitting integrals come from the same generator approach
(`scripts/gen_1e.py`, `scripts/gen_df.py`, `scripts/gen_df_grad.py`). They run
over `trc_pairlist_t`, a screened list of shell pairs with their primitive
pairs, one `do concurrent` iteration per pair, writing without atomics.

## 6. The SCF

`trc_scf_run` (`src/scf/trc_scf_driver.F90`) runs restricted and unrestricted
Hartree–Fock and Kohn–Sham.

### 6.1 Once per geometry

`scf_ctx_t` (`src/scf/trc_scf_context.F90`) builds, in order: the pair list;
the one-electron matrices (Cartesian, folded to the run's AO space); the
four-centre engine (unless the run is density-fitted); the nuclear
repulsion; the linear-algebra handles; the orthogonaliser X by canonical
orthogonalisation, dropping overlap eigenvalues below 10⁻⁸; the PCM cavity;
and the DFT grid with its separate VV10 grid. The DFT grid can be kept
(`trc_grid_cache_t`) for a later gradient.

### 6.2 Initial guess

- **SAD** [superposition of atomic densities]: unrestricted Hartree–Fock
  on each distinct element in the run's basis (Hund occupations),
  spherically averaged, cached per element and placed block-diagonally.
  **SADQ** runs the atoms restricted with fractional occupations, for
  charged systems.
- **SAP** [3]: the superposition of fitted atomic potentials, added to the
  core Hamiltonian and diagonalised.
- **GWH** and the core Hamiltonian, or a density supplied by the caller.

### 6.3 One iteration

1. Fold the density to the Cartesian space.
2. Two-electron matrix: `eri%fock_resident` on the device-resident density
   (or the DF build, section 8), plus the long-range exchange pass for a
   range-separated functional. An unrestricted run builds J from the total
   density and K per spin.
3. Exchange-correlation potential and energy (section 7), including VV10.
4. PCM reaction potential at the total density (section 10).
5. Energy E = Tr(DH) + ½Tr(DG) + E_xc + E_nuc + E_pcm.
6. Fock matrix F = H + G + V_xc + V_pcm and the error vector
   Xᵀ(FDS − SDF)X.
7. Extrapolation, then the eigenproblem F′ = XᵀFX and the new density, on
   the device through cuSOLVER.

Convergence requires |ΔE| < 10⁻¹⁰ and ‖FDS − SDF‖ < 10⁻⁵ by default.

### 6.4 Convergence acceleration

- **CDIIS** [4] over a ring buffer of 10 Fock/error pairs, with cached
  inner products. A restricted run uses it from the first iteration; an
  unrestricted run damps first and switches CDIIS on once the commutator
  norm falls below 0.5, since unconstrained extrapolation far from
  convergence can overshoot.
- **ADIIS** [5] before CDIIS starts, as an option: it minimises an energy
  functional over the convex hull of earlier densities, so it only moves
  towards densities already visited. ADIIS and CDIIS switch rather than
  blend.
- Level shifting and damping while neither extrapolation is active
  (unrestricted runs damp for at least four iterations).

### 6.5 Incremental Fock build

As an option (`--incremental`), later iterations build G from the change in
the density, G(D) = G(D_ref) + G(D − D_ref), which is exact because G is
linear in D. The density difference shrinks as the SCF converges, so the
density-weighted screen discards more quartets. Two safeguards keep the
energy correct: the difference build uses a threshold 10⁻⁴ times tighter
than a full build (a fixed absolute threshold applied to a vanishing
density bounds nothing), and increments begin only once the commutator norm
is below 10⁻², with a full rebuild every 20 iterations.

### 6.6 Several GPUs

Every rank runs the same loop. The Fock build, the XC integration and the
PCM integrals are split across ranks and summed. Extrapolation, the
eigenproblem and the new density run on rank 0, and the density is
broadcast every iteration, since two devices need not return the same
eigenvectors for a degenerate subspace.

## 7. Density functional theory

### 7.1 Grids

Molecular grids (`src/grid/`) combine per atom:

- a Treutler–Ahlrichs M4 radial grid [6] with per-element ξ;
- Lebedev–Laikov angular grids [7];
- NWChem-style angular pruning in five radial zones;
- Becke's partition of space [8] with Treutler's atomic size adjustment,
  or Stratmann's screenable partition [9].

Grid sizes per element come from levels 0–9 (default 3). VV10 has its own,
coarser grid (default level 1).

### 7.2 Exchange-correlation integration

The integration follows the batched dense-density design of Stocks and
Barca [10] (`src/xc/trc_xc.F90`, `src/xc/trc_xc_batch.F90`):

1. Points are partitioned into spatially compact batches by bisection
   along the longest axis; each batch keeps the list of shells that reach
   it, from per-shell cutoff radii.
2. Batches whose density bound Σ|D_μν|·m_μ·m_ν falls below a tolerance are
   dropped.
3. Per batch: collocate the basis functions (and gradients) on the points;
   gather the batch's local density block D_b; form X = χ D_b with a GEMM;
   evaluate ρ, ∇ρ and the functional at the points; form χᵀZ with a second
   GEMM; scatter into V_xc with atomics.
4. Batches are padded to a few fixed shapes and grouped, so each group is
   one strided-batched GEMM.

Meta-GGAs add the kinetic-energy density τ from three more GEMMs with the
basis-function gradients. Several GPUs split the batches by cost and sum
V_xc.

### 7.3 Functionals

terco implements the functional kernels itself rather than linking libxc.
The kernels are translated to Fortran from ExchCXX's Maple-generated C++
(`tools/exchcxx_to_fortran.py`, `src/xc/functionals/`), and the registry of
functionals (`src/xc/trc_xc_functional.F90`, `docs/functionals.md`) is
generated from ExchCXX's functional table. Every translated kernel is
checked against libxc [11] in `test/check_xc.F90`. 69 functionals run:
LDA, GGA and meta-GGA, global and range-separated hybrids, VV10 and double
hybrids.

- **Range-separated hybrids** use the long-range exchange pass of
  section 4.7.
- **VV10** [12] nonlocal correlation is evaluated by direct double
  summation over its own grid, split across ranks.
- **Double hybrids** run the SCF with the semilocal part and the
  exact-exchange fraction, then add the RI-MP2 correlation (section 9)
  scaled by the functional's opposite- and same-spin weights.

## 8. Density-fitted J and K

`df_jk_t` (`src/scf/trc_scf_df.F90`) fits both J and K [13]:

- **Setup, once.** The metric M = (P|Q) and its Cholesky factor L
  (M = LLᵀ, never inverted); the three-centre integrals (μν|P), packed over
  μ ≥ ν, and B = T L⁻ᵀ by one triangular solve. L is kept for the gradient.
- **Each iteration.** J from two GEMVs on the packed B. K from a
  factorisation of the density: D is diagonalised, its eigenvalues are cut
  relative to the largest, and the positive and negative parts give factors
  Y₊ and Y₋. B is unpacked block by block in auxiliary functions (the block
  size chosen from free device memory), Z = B Y by batched GEMM, and K
  accumulates Z Zᵀ.

The fitted build is closed-shell and not range-separated. RI-MP2 reuses B
when its auxiliary basis is the same.

## 9. RI-MP2

The RI-MP2 driver (`src/post_hf/rimp2/trc_rimp2_driver.F90`) forms the
fitted three-index integrals (ia|P), transforms with B = X L⁻ᵀ, and for each
pair of occupied orbitals builds the (ia|jb) block by GEMM and accumulates
the opposite- and same-spin energies. On several GPUs the occupied orbitals
are split into contiguous blocks, one per rank, and blocks circulate in a
ring so that each unordered pair is computed by exactly one rank, following
Stocks, Palethorpe and Barca [14]. A CUDA-aware MPI receives device buffers
directly; otherwise the blocks go through the host. Unrestricted RI-MP2 runs
on one GPU.

## 10. Polarisable continuum

`trc_pcm_t` (`src/solvation/trc_pcm.F90`) implements C-PCM and IEF-PCM on a
cavity discretised with the switching/Gaussian (SWIG) scheme of Lange and
Herbert [15]: Lebedev spheres around each atom, with a smooth switching
function removing buried points. Radii are the modified Bondi set [16, 17]
scaled by 1.2.

The response matrix K (S for C-PCM, S − f/2π · DAS for IEF-PCM) is LU-factored
once on the device. Each SCF iteration computes the electrostatic potential at
the surface points, solves for the charges, and adds the operator built from
them to the Fock matrix of both spins. The potential and operator integrals
are split across ranks by surface point.

## 11. Response and gradients

- **Polarisabilities** solve the coupled-perturbed Hartree–Fock equations
  [18] (`src/scf/trc_cphf.F90`) and their Kohn–Sham counterpart
  (`src/scf/trc_cpks.F90`, adding the XC kernel response) by preconditioned
  conjugate gradients, with the orbital-Hessian products from the
  non-symmetric Fock build.
- **Nuclear gradients** (`src/scf/trc_scf_grad.F90`) combine the
  one-electron derivative integrals with the energy-weighted density, the
  four-centre or density-fitted two-electron derivatives, the XC gradient
  including the grid-weight response (from the derivatives of the Becke
  partition), the VV10 gradient and the nuclear repulsion.

## 12. GPU programming model and data ownership

All persistent device data has one owner, which maps it on construction and
releases it explicitly:

| Owner | Device data | Released by |
|---|---|---|
| `trc_basis_t` | shell and primitive arrays | `release` |
| `trc_pairlist_t` | shell pairs and primitive pairs | `release` |
| `trc_eri_t` | primitive pairs, bins, Schwarz and density bounds, decontraction maps | `release` |
| `trc_xc_grid_t` | the batched grid | `release` |
| `scf_ctx_t` | S, H, X, the pair list, the ERI engine, the PCM cavity, the grid cache | `release` |
| `scf_state_t` | Fock, density and work matrices | `release_device` |
| `cdiis_t`, `adiis_t` | the DIIS history | `release_device` |
| `df_jk_t` | B, the Cholesky factor, work arrays | `release` |
| `trc_pcm_t` | the surface and its operators | `release` |
| `trc_linalg_t` | cuBLAS/cuSOLVER handles and workspace | `release` |

Transient arrays are mapped and unmapped within the call that uses them.
Constant tables (the Boys function, Cartesian index tables, Rys roots) are
declared on the device once. A `do concurrent` body calls only intrinsics and
`pure` routines marked `!$acc routine seq` in the same module, with
explicit-shape arguments and per-thread scratch declared inside, which is
what lets nvfortran inline it.

**Portability.** `tools/dc_to_omp.py` and `tools/acc_to_omp.py` translate the
same sources to OpenMP (target offload or host threads), and CI runs the
host-threaded translation at four threads.

## 13. Kernel generators

| Generator | Output |
|---|---|
| `gen_perclass.py` | HGP Fock kernel per class, and the skeleton the Rys kernels are spliced into |
| `gen_vrr.py`, `gen_hrr.py` | unrolled recurrences used by the above |
| `gen_rys.py`, `gen_rys_grad.py` | Rys Fock and gradient kernels per class |
| `gen_rys_roots.py` | Rys root and weight tables |
| `gen_1e.py` | one-electron, multipole, PCM and derivative integrals |
| `gen_df.py`, `gen_df_grad.py` | two- and three-centre DF integrals and their derivatives |
| `gen_boys_table.py` | the Boys interpolation table |

The kernels for the default build (angular momentum up to d) are committed in
`src/generated/`; other builds (`TERCO_LMAX=3`, other Cartesian orders)
regenerate at configure time.

## 14. Interfaces

- **Fortran API** (`src/api/trc_api.F90`): the basis, the pair list and the
  integral entry points; `trc_eri_t` for Fock builds; `trc_scf_run`.
- **C ABI** (`src/api/trc_capi.F90`, generated `include/terco.h`): an opaque
  context created with `trc_create`, configured with `trc_set_*`, run with
  `trc_run_scf` (then optionally `trc_run_rimp2`, `trc_run_gradient`,
  `trc_run_polarizability`), read with getters and freed with `trc_destroy`.
  Every call returns a status code and a reason. A host program passes its
  own MPI communicator; terco duplicates it and binds one GPU per rank.
- **Command line** (`app/`): the `terco` program, driving the C ABI, with a
  JSON summary and restart files.

## 15. Validation

- **Anchors**: reference values from pyscf and libcint
  (`test/pyscf_refs/`), generated offline. Each reference carries a hash of
  the code that produced it, so a change to the generating script makes the
  check fail until the reference is regenerated.
- **Goldens**: terco's own numbers at tight tolerances (`test/goldens/`),
  to catch any drift.
- **Translated functionals** against libxc, and the host build against the
  device build.
